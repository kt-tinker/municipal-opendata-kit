# 設計メモ：何を型にし、どこに AI を挟むか

## 背景

草加市のオープンデータ5種類を標準形式に整えたとき、作業の多くは繰り返しでしたが、
次の3か所で「人が見ないと決まらない」判断が発生しました。

1. 元の列名と標準の項目名の対応づけ（市ごとに列名が違う）
2. 位置の付け方の判断（同名施設の照合、番地まで特定できない住所）
3. 資料間の食い違い（同じ施設なのに資料によって番地が違う）

このキットは、繰り返し部分をコードに、判断部分を「確認リスト → AI の一次判断 → コードによる検証 → 人の最終確認」の流れにしています。

## 判断の流れ

```
build ──▶ review/queue.json（確認待ち）
              │
              ▼
        Claude Code /odkit-review（根拠付きで判断。迷えば needs_human）
              │
              ▼
        review/decisions.json（判断の記録。by / reason / confidence 付き）
              │
              ▼
build ──▶ 判断をコードで検証して反映。通らない判断は rejected_decision 付きで確認リストに戻る
```

- 判断はすべて `decisions.json` に残るので、後から「誰が・なぜそう決めたか」を追える
- 確認リストに残るのは「AI も判断できなかったもの」と「検証に通らなかったもの」だけになる

## AI に任せないこと

| 任せないこと | 理由 | 代わりに |
| --- | --- | --- |
| 緯度・経度の数値を書く | もっともらしい誤りを見抜けない | 座標は元データ・公共施設情報・国土地理院からのみ取る |
| 元データにない値を埋める | 公的データとして事実でなくなる | 空欄のまま |
| 食い違いの「正解」を決める | 正しいかどうかは市にしかわからない | 採用した方と違いを README に明記し、市への確認事項にする |

## 位置の精度の記録

各行の備考欄に、位置をどう付けたかを決まった文言で書きます。地図アプリ側はこの文言で精度を色分けできます。

| 精度 | 備考の文言（含まれる語） |
| --- | --- |
| 元データ | （なし）／度分秒を10進数に変換 |
| 公共施設情報から転記 | 同名施設 |
| 住所検索（番地） | 住所検索 |
| 住所検索（街区） | 街区レベル |
| 町字の代表点 | 町字の代表点（要確認） |

## 横に広げるときの課題

- **元データの不ぞろい**：市によって列の粒度や形式（Excel・PDF）が違う。PDF は対象外
- **住所**：「地内」「付近」、建物名の混在など例外が多い。丁目を省いた書き方（川口市の「青木2-1-1」）は住所の形だけでは丁目か番地か決まらない。
  → アドレス・ベース・レジストリの町字マスターと照らす方式にした（3市目の川口市で導入）。マスターにない町字は採用せず確認リストに回す
- **市外の施設**：市が市外に持つ施設（臨海学園・少年自然の家）は市域の範囲チェックに引っかかる。住所が市外のものは範囲チェックの対象外とし、README に一覧を出す
- **市境**：隣の市のデータがないと、市境の近くで「近くの施設」が見つからない。複数の市を同じ形式で整えて初めて解決する
- **登録と保守**：BODIK などへの登録・更新は人と組織の作業。元データの更新に追従する担い手が必要
