# 市町村を追加する（通し作業）

利用者から市町村名（と、わかれば元データの場所）を受け取り、標準形式の CSV と README ができ、
人の確認が要るものだけが残った状態まで進める。途中の判断は根拠を残し、迷ったら人に回す。

## 守ること（最優先）

- **座標の数値を書かない。** 緯度・経度・市の範囲（bbox）の数値を設定ファイルや判断記録に書いてはいけない。
  位置は元データ・公共施設情報・国土地理院の結果からだけ取られる。bbox は `"auto"`
- **元データを書き換えない。** 直すのはキットの設定・コードと判断記録（decisions.json）だけ。元の値は README の「直した箇所」に残る
- **標準の項目名を変えない。** `standards/` の定義と完全に一致させる
- **work/ と output/ を git に入れない。** 公開してよいのはキットのコード・設定・テストだけ
- **push・PR・メール送信などの外に出る操作は、利用者の了承を得てから。** ブランチを切って commit までは進めてよい
- 次のときは止めて利用者に聞く：対象のデータが PDF しかない／ライセンスがオープンでない（PDL1.0・CC BY 以外）／
  全国地方公共団体コードの根拠が見つからない／ネットワークに出られない

## 手順

### 1. 元データを探す

- 埼玉県内：`python -m odkit discover <市名> --slug <英字名>` で県のポータルから候補を探す（`work/<slug>/discover.json`、`cities/<slug>.draft.toml` ができる）
- 県外、またはポータルにないもの：市のサイトや都道府県のポータルを調べるか、利用者に URL を聞く
- 対象は AED・指定緊急避難場所・公共施設・文化財・観光施設の5種類。見つからない種類はそのまま「なし」として記録する
- データセットごとに、ページの URL・ファイルの URL・形式・ライセンス・更新日を控える（ポータルの更新日が古く、リンク先の市のサイトのほうが新しいこともある）

### 2. 設定ファイルを作る

- 下書き（なければ `cities/soka.toml`）を `cities/<slug>.toml` に写し、`[city]` を埋める
  - `code`：全国地方公共団体コード（6桁）。ファイル名や「全国地方公共団体コード」の列で確かめる
  - 政令指定都市は `[city.wards]` に区の名前と団体コードを書く（`cities/saitama.toml` が例）
  - `bbox = "auto"`
- `python -m odkit fetch cities/<slug>.toml`（元データと町字マスターの取得）
- `python -m odkit inspect cities/<slug>.toml` の結果を見て、`/odkit-map-columns` の規則で列を対応づける
  - すでに標準の列名なら `passthrough = true`
  - 迷った対応には `# 要確認：<理由>` を付け、最後の報告に入れる

### 3. 整形する

- `python -m odkit build cities/<slug>.toml`
  - 初めての市は住所検索に時間がかかる（1件1〜2秒。1,000件なら30分ほど）。途中で止めても検索結果は残る
  - エラーで止まったら、設定（列名・文字コード・形式）を直してやり直す
  - 「町字マスターが〇〇市のものではありません」→ code（wards）の誤り

### 4. 確認待ちを仕分ける

`work/<slug>/review/queue.json` を読み、まず **同じ形のものがまとまって出ていないか** を見る。

- **同じ書き方の住所が何件も分けられない、同じ理由で何件も止まる** → 個別に判断せず、キットのコードで決まった形に直す
  - これまでの例：丁目を省いた住所、丁目のある区域とない区域が混在する町、大字の有無の揺れ、
    「字〇〇」の小字、「地内番」「無番地」、1つの欄に複数の場所、市外の施設、`(048)-` の電話番号
  - 直したら `tests/test_odkit.py` にその市の実際の値でテストを足し、`python -m unittest discover tests` が全部通ることを確かめる
  - テストの元データ（fixtures）には実データの行をそのまま使う。座標の数値を作らない
- **1件ずつ事情が違うもの** → `/odkit-review` の基準で decisions.json に判断を書く

### 5. 判断を反映する

- もう一度 `build` し、`rejected_decision` が付いて戻ったものは判断を見直す
- 確認待ちが `needs_human`（人の判断待ち）だけになるまで 4〜5 を繰り返す

### 6. 報告する

利用者に次を日本語で伝える。

1. データセットごとの表：件数／元データで位置あり／キットで付けた位置（住所検索・公共施設から転記・町字の代表点）／位置なし
2. 直した表記の主なもの（`output/<slug>/README.md` の「元データの表記を直した箇所」）
3. 人の確認が必要なもの（市への確認事項として、理由つき）
4. その市の元データの特徴（ほかの市との違い。市へのフィードバックの材料）
5. キットのコードを直した場合はその内容

あわせて README の「設定例」の表に1行足し、ブランチに commit する。push してよいか利用者に聞く。
